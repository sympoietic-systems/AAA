## Current architecture: strengths

- Admission now distinguishes emitted candidate review from metabolic lifecycle. Local `m060` work records explicit-tag receipts with source IDs and hashes, bounded comparisons, policy/evaluator metadata, and shadow-only recommendations; it explicitly leaves adoption to human review. See `docs/decisions/ADR-115-shadow-belief-admission.md:14-30`, `backend/services/belief_admission.py:48-63,73-105,108-150`, and `backend/storage/migrations/m060_belief_admission.py:1-20`. This is an auditable, bounded gate for one previously implicit path.
- Existing metabolic pathways preserve differing signals: chat and web use 16D cosine match plus concept-density threshold for unmatched inputs; matched inputs accrete with alignment and source weight. Ghost similarity can boost/dampen initial mass. See `backend/modules/belief_engine.py:134-190,284-310,467-499`, `backend/modules/belief/perception_handlers.py:143-176`, and `docs/systems/BELIEF_SYSTEM.md:181-212`.
- Attentional context is constrained and diversified: top-mass anchors, lower-confidence/stressed beliefs, optional Jev salience, then distinct structural-cosine candidates; collapsed/faded and low-confidence nodes are excluded. See `backend/utils/prompt_builder.py:83-123,125-202`.
- Decay includes both turn-based omission and a separately callable wall-clock atrophy path, with event logging in the latter. Crystallized nodes have a configured mass floor for omission decay. See `backend/modules/belief/decay.py:15-94,96-185`; actual runtime schedule needs to be checked against daemon wiring/config before claiming which path is operational.

## Risks / gaps

- Explicit-emission admission is not system-wide admission. Passive chat concept-density nucleation, shared-note nucleation, web retrieval, perception, and conversational-pattern paths still call `_nucleate_proto_belief` directly, bypassing the new receipt and its source/evidence checks. See `backend/modules/belief_engine.py:467-499` and `backend/modules/belief/perception_handlers.py:93-139,143-176,182-210`; ADR-115 acknowledges legacy non-tagged paths are outside its gate (`docs/systems/BELIEF_SYSTEM.md:119-127`). This is the main false-positive/traceability gap.
- The `BELIEF_SYSTEM.md` document is internally inconsistent about decay: §4.D says silence/idle does not decay and asserts the daemon's 15-minute atrophy is disabled (`:216-243`), while §6.A says atrophy is exclusively run every 15 minutes (`:357-361`). Code contains both turn decay and callable time-based atrophy; no schedule should be asserted from these conflicting prose claims alone. Reconcile docs with current daemon/config wiring.
- Turn decay silently catches per-belief persistence failures, and atrophy also catches and continues (`backend/modules/belief/decay.py:70-84,147-175`). This can make partial decay persistence hard to distinguish from a successful sweep without explicit receipts/metrics.
- Belief resonance is structural-vector similarity, while admission's comparison nomination is token-overlap Jaccard and optional evaluator judgment. These answer different questions; avoid treating either as semantic equivalence. `backend/services/belief_admission.py:37-45,108-145`; `backend/modules/belief_engine.py:284-310`. The shadow floor/evaluator is documented provisional and uncalibrated (`ADR-115:28-30`).
- Legacy architecture prose overstates guarantees: the attractor prose says structural topology “guarantees” non-semantic lateral lines (`docs/systems/BELIEF_SYSTEM.md:326-331`), but runtime only selects max cosine over available, non-used beliefs and may have no slot-six candidate (`backend/utils/prompt_builder.py:151-189`). Treat as a selection heuristic, not a guarantee of conceptual novelty.
- Candidate receipts are explicitly assessment records; their comparisons use lexical overlap to choose at most ten records (`backend/services/belief_admission.py:37-45,108-122`). Record snapshots are useful for audit but cannot demonstrate candidate truth, uniqueness, or admission quality absent calibrated evaluation.

## Priorities

1. Keep `m060` claims explicitly local/unverified until migration and deployment state are independently established; shadow recommendation must remain non-authoritative unless a future calibrated policy is separately reviewed.
2. Close or deliberately preserve the passive-path boundary: inventory each direct proposal creator, decide its required provenance/evidence standard, and record origin-specific audit data. Do not imply ADR-115 adjudicates historical/passive proposals.
3. Resolve decay documentation against daemon call sites and config, then report the operative schedule and distinguish turn omission from elapsed-time atrophy. Add observable counts/failures if partial sweeps are operationally consequential.
4. Calibrate admission and retrieval separately against labeled examples: lexical duplicate nomination, semantic paraphrase/conflict, and structural resonance should have distinct evaluation targets.
5. Reword attractor/dream claims as heuristics until measured; selection geometry can create routes for lateral recall but alone does not establish semantic novelty or useful dream outcomes.

## Runtime resolution: decay schedule and passive creation thresholds

### Decay: local code/config call path

- **Elapsed-time atrophy is disabled in the current local configuration.** `backend/config.yaml:190-191` sets `belief_ecosystem.wall_clock_decay.enabled: false`. The daemon reads that flag and only calls the engine atrophy method when true and the interval elapsed (`backend/metabolisation/daemon.py:205-226`). Its interval is 900 seconds (15 minutes), initialized at `:144-145`; this is a conditional cadence, not evidence of active decay at present.
- **Turn-based omission decay is enabled.** `backend/config.yaml:186-189` sets `turn_decay.enabled: true`, `decay_per_turn: 0.0005`, and crystallized floor `0.55`. It is called directly from `BeliefDynamicsEngine.metabolize()` after considering the input (`backend/modules/belief_engine.py:501-505`), and `DecayManager` decays active beliefs except the single matched/engaged ID (`backend/modules/belief/decay.py:15-57`). Relevant chat and dream execution paths invoke `belief_metabolism.metabolize` (`backend/services/chat.py:598`; `backend/metabolisation/dream_execution.py:131`; `backend/metabolisation/dream_trigger_policy.py:294`; `backend/metabolisation/scheduler.py:316`). So code/config support an operative turn-decay path for these calls, subject to those flows running successfully.
- The text of `BELIEF_SYSTEM.md:216-243` that says turn decay happens on chat/dream activity aligns with this code/config; its claim at `:222` that periodic atrophy is disabled also aligns with current config. The separate `:357-361` statement that atrophy is “called exclusively” every 15 minutes is stale/misleading because the call is guarded by disabled config and no longer exclusive relative to turn decay. Note legacy `backend/metabolisation/mass_decay.py` also checks wall-clock flag but appears separate; daemon's shown scheduled call is `engine._atrophy_beliefs`, not `_apply_mass_decay` (`daemon.py:205-226`; `mass_decay.py:16-45`).

### Passive proposal thresholds and checks before direct proposal creation

`BeliefDynamicsEngine._NUCLEATION_THRESHOLD` is `AAA_BELIEF_NUCLEATION_THRESHOLD` or `0.2` by default (`backend/modules/belief_engine.py:35-36`). `calculate_concept_density` computes `tanh(matched cybernetic dimensions / 3.0)` by default (`backend/modules/belief_math.py:16-28`); at the default 0.2 threshold, one matched dimension yields about 0.32, above the threshold. The threshold is an environment override, not a `config.yaml` value.

- **Chat user-turn path:** first finds the most similar active belief; if one meets the default 0.2 similarity threshold it accretes, otherwise a proposal is created only when concept density is strictly greater than 0.2 (`belief_engine.py:467-499`). This checks active belief resonance but not pending proposals or exact statement/scope/time duplicates. It does not verify source authority/evidence beyond using the stored user message as source. Ghosts only modulate initial mass at similarity >0.7 or >0.9; this does not block proposal creation (`belief_engine.py:143-190`).
- **Document perception:** checks non-collapsed/non-faded beliefs and creates a proposal when best similarity is below 0.2 (`perception_handlers.py:34-46,75-85`). It has no concept-density minimum and does not check pending proposals. If `belief_nodes_implicated` is supplied, the comparison set is restricted to those nodes (`:42-45`), potentially making a candidate look novel relative to that restricted set. Source ID/type are passed through but no source-authority/evidence validation appears in this function.
- **Shared note:** accretes only when best active-belief similarity is strictly above 0.85; otherwise it always creates a proposal, without a density gate (`perception_handlers.py:108-139`). It maps the proposal source type to `chat_turn` and source ID to `message_id` (`:131-137`), so provenance is coarse/misaligned with the `shared_note` input path. No pending-proposal dedup or source-authority check is visible.
- **Web retrieval:** accretes a nearest active match at the default 0.2 threshold; otherwise it creates when concept density is strictly above 0.2 (`perception_handlers.py:151-176`). No pending-proposal dedup or source/evidence authority check is visible; source metadata is labeled `web_probe`.
- **Conversational pattern:** returns only when density is below 0.2; at exactly 0.2 or above, a matching active belief accretes, otherwise it creates a proposal (`perception_handlers.py:182-218`). No pending-proposal dedup or source-authority check is visible; source attribution is the generic `chat_turn`/`cross_conversation` pair.

For these direct belief proposal creators, the common dedup boundary is therefore “matches an active belief in 16D structural cosine space”; pending/refined proposals are not included in `_find_closest_active_belief` (it reads `list_beliefs`) and there is no exact textual/scope/time guard before `create_proposal`. Collapsed ghosts may boost/dampen mass but do not prevent a new proposal. These are local code observations, not claims about production configuration or event frequency.

A separate CommitmentStore creates **commitments**, not belief proposals: it requires at least three active beliefs, orphan clusters of at least two, mass threshold, sustained tension across three daemon cycles, and duplicate-label exclusion (`backend/modules/commitment_store.py:201-268,270-312`). That is a distinct downstream subsystem and should not be treated as an admission guard on the direct `_nucleate_proto_belief` calls above.

## Snapshot/event interpretation addendum

### Confidence and lifecycle semantics

- Reinforcement/conflict confidence update is distinct from mass: `plasticity = dc * ((1 - alignment) / 2)` and `delta_confidence = plasticity * alignment * perturbation / max(current_mass, 0.01)` (`backend/modules/belief_math.py:60-62`). The engine adds this delta to the old confidence and clamps to `[0,1]`; mass is updated separately using its own formula/clamp (`backend/modules/belief_engine.py:204-210`; `backend/modules/belief_math.py:55-70`). Thus an atrophy-only event does not imply confidence should fall.
- Lifecycle stage is not recomputed from the crystallization threshold on every mass update. `compute_lifecycle_stage` collapses below confidence 0.20 or mass 0.02; it crystallizes nucleation/accretion at mass >=0.5, then preserves a current `crystallized` stage (`backend/modules/belief_math.py:73-101`). Turn decay separately preserves the crystallized label and applies the 0.55 floor based on existing stage (`backend/modules/belief/decay.py:49-68`).
- Wall-clock `atrophy_beliefs` does **not** use that turn-decay floor or recompute crystallization. It carries forward the prior stage and only changes it when mass falls below 0.02 (`backend/modules/belief/decay.py:139-155`). Therefore a crystallized belief below 0.55, including the supplied snapshot range down to 0.1278, is mechanically possible if this path ran; it is not by itself proof of an illegal stage transition. At mass below 0.02 it would be marked collapsed. The all-confidence-1.0 observation is compatible with atrophy because atrophy writes back the unchanged confidence (`:147-155`).

### Atrophy accumulation risk if wall-clock decay is enabled

- `hours_since` is recalculated from the original `last_reinforced_at` every sweep (`backend/modules/belief/decay.py:112-129`). The update calls `update_belief_mass(..., touch_reinforced=False)`, which intentionally leaves `last_reinforced_at` unchanged (`:155`; `backend/storage/repositories/cognitive/belief.py:184-196`). Consequently each later sweep applies a loss proportional to the **total** elapsed hours again, against the already-reduced current mass, capped at 20% each sweep (`decay.py:131-134`), rather than applying only the hours elapsed since the previous sweep. If enabled, repeated sweeps can over-apply elapsed-time decay; once elapsed time exceeds the cap horizon, each sweep can remove up to 20% of remaining mass. This path also bypasses the crystallized 0.55 floor. Both are code-level risks conditional on atrophy actually being invoked; local config currently disables it (`config.yaml:190-191`), while the user-provided production snapshot/event pattern alone does not establish what production config was at the time.

### Event/API field naming

`belief_events.impact_score` is a generic event impact in storage (`backend/storage/models.py:202-212`; repository inserts the supplied `impact` unchanged at `backend/storage/repositories/cognitive/belief.py:312-332`). For accretion, the engine supplies `delta_m` (mass delta) (`backend/modules/belief_engine.py:226-235`); for atrophy, it supplies `new_mass - current_mass` (also mass delta) (`backend/modules/belief/decay.py:157-169`). However `serialize_belief_event` exposes this value as `delta_confidence` (`backend/services/belief_serializer.py:27-40`). That API field is semantically mislabeled for these paths: it is the stored generic impact, and in both cited paths specifically a mass delta, not the calculated confidence delta. This is a concrete telemetry/UI interpretation defect; the event rationale separately carries current mass/confidence text, but is not a normalized confidence delta.
